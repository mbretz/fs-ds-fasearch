# Monorepo: Design System + Store Locator — Portfolio Showcase

## Context

You want a public StackBlitz-hosted monorepo as a portfolio piece that demonstrates:

1. **Design-system engineering** — a Radix-style, fully composable component library driven by tokens authored in Figma.
2. **Product composition** — a store-locator app that consumes the DS both as off-the-shelf components and as primitives composed into new product-level components.

Constraint: the showcase has to boot quickly on StackBlitz WebContainers for reviewers clicking your link. That tips us away from heavyweight tooling and toward a clean, fast cold start. The DS is built in its entirety before the locator begins.

## Radix vs shadcn: Recommendation

**Use Radix Primitives directly as your foundation. Reference shadcn for recipes but do not install it.**

- **Radix UI Primitives** (`@radix-ui/react-*`) — unstyled, accessible, headless components (Dialog, DropdownMenu, Popover, Tabs, etc.). This is a real npm dependency you install.
- **shadcn/ui** — not a library. It's a registry of copy-paste component files built _on top of_ Radix Primitives with Tailwind styling. You own the code.

For a **portfolio piece showcasing DS engineering**, copy-pasting shadcn undersells the work. Instead:

- Take Radix Primitives as the accessibility/behavior foundation.
- Use shadcn's source as a reference for proven patterns (`asChild`, slot composition, ref forwarding, variant cva recipes), but author each component yourself against your own tokens.
- This produces a real, ownable component library — not a wrapper around shadcn — and visibly demonstrates DS thinking (theming, slot APIs, composition primitives) rather than wiring skills.

Net: **Radix Primitives + cva + Tailwind + your tokens**, with shadcn as a reference book on the shelf.

Two apps + four packages — one package per Figma library, except the Assets library (Icons + Illustrations pages) which splits into two packages since the two asset types have materially different color handling. This mirrors how the design source is organized, which is both a clarity win and a portfolio narrative ("code structure tracks design structure").

Workspace deps:

- `packages/ds` → `packages/tokens`, `packages/icons`
- `packages/icons` → `packages/tokens` (icons may reference color tokens for `currentColor` defaults / sizing)
- `packages/illustrations` → no workspace deps (multicolor SVGs carry their own fixed palette, not token-driven)
- `apps/locator` → `packages/ds` (and transitively `tokens` + `icons`), and optionally `packages/illustrations` directly (e.g. empty states)
- `apps/storybook` → `packages/ds`, `packages/illustrations`

Consumers import from each package directly (`@scope/tokens`, `@scope/icons`, `@scope/illustrations`, `@scope/ds`) — the DS does **not** re-export icons or illustrations. Keeping the packages separate preserves the Figma-mirror story and lets the locator pick icons or illustrations à la carte without dragging in the whole DS.

## Phase 1: Design System (`packages/ds`)

### 1.1 Token Pipeline (Figma "Styles" library → code)

Tokens are authored as native Figma Variables. The pipeline was originally scoped as free-plugin-only (see history note below), but is now a **one-time Tokens Studio Pro export**: Figma Variables were imported into Tokens Studio, cleaned up there (naming, typing, the `value`-as-token-name collision fixed — see §1.2), and exported once as a multi-file DTCG set. There is no live sync provider configured — re-syncing later means re-running the same manual export + adapter steps below, not an automatic pull.

1. **Author in Figma "Styles" library** — tokens live as native Figma variables, organized into collections (`color`, `density`), with names slash-delimited to match Figma's group separator (`color/bg/primary`, `density/padding/sm`). The `color` collection has two modes: `light` (primary) and `dark`. The `density` collection has two modes: `roomy` (default) and `condensed`. See §1.2 for naming conventions and §1.4 for the density system.
2. **Export from Tokens Studio Pro** — Figma Variables are imported into Tokens Studio, where each Figma Variable Collection becomes a Theme Group and each mode a Theme. Exporting via "Export file/folder" → "Multiple files" produces one JSON file per token set (`primitives/primitives.json`, `semantic/semantic.json`, `component/component.json`, `color/light.json`, `color/dark.json`, `density/condensed.json`, `density/roomy.json`), plus `$themes.json` (which sets compose into which Theme) and `$metadata.json` (`tokenSetOrder`, the merge precedence across sets). All committed as-is to `packages/tokens/source/tokens-studio/`.
3. **Merge with the Tokens Studio adapter** — `packages/tokens/scripts/tokens-studio-adapter.ts` reads `$themes.json`/`$metadata.json` to derive the group→mode→set mapping (not hardcoded to the current 7 file names), merges the sets into a single tree matching the collection/mode shape below, and normalizes each leaf from DTCG's `$value`/`$type`/`$description` to this project's `value`/`type`/`description` convention. Output replaces `packages/tokens/source/tokens.json`, which downstream tooling still consumes unchanged.
4. **Transform with Style Dictionary** — `packages/tokens/sd.preprocessors.ts` (rename the `value`-as-token-name collision, remap collection-relative aliases to full paths, resolving mode-relative references against each leaf's own enclosing mode) and `sd.transforms.ts` (path-based dimension/fontWeight/number classification, since even Tokens Studio's declared types don't fully disambiguate — see §1.2) feed into two build scripts:
   - `packages/tokens/scripts/build-tokens.ts` — multi-mode build (light+roomy / dark+roomy / light+condensed), diffed to produce:
     - `build/css/tokens.css` — base values on `:root` (light/roomy), including canonical mode-collection passthrough variables (e.g. `layout.*` colors, the raw density scale) that aren't yet referenced by any component
     - `build/css/dark.css` — sparse `[data-theme="dark"]` overrides (only tokens that actually differ from light)
     - `build/css/density.css` — `[data-density="roomy"]` and `[data-density="condensed"]` blocks, full in both (no single implicit default to diff against)
   - `packages/tokens/scripts/build-dtcg.ts` — `build/dtcg/tokens.{color}-{density}.json`, one fully-resolved, spec-compliant DTCG file per mode combination (no aliases, auto-generated `$description`s), for consumers outside this codebase (other tools, agents) that just need a self-contained token set.
   - `build/ts/tokens.ts` — typed token object (optional, for non-Tailwind consumers) — not yet built.
5. **Consume in DS** — `packages/ds/src/theme.css` imports the `build/css/*.css` files. Components reference Tailwind classes that resolve to CSS vars. See the deviation note directly below — this file is CSS, not `tailwind.preset.ts`, and colors are consumed as bare hex-valued vars, not `hsl(var(--...))`.
6. **Validate** — the `tokens-json-review` skill (`.claude/skills/tokens-json-review/`) checks `packages/tokens/source/tokens.json` for double-encoding, unit-suffix correctness (type-aware: a unit is only wrong on a non-`dimension`-typed token), mode key-parity, and alias resolution before it's trusted as a build input.

**Deviation from plan (2026-08-12): `theme.css`, not `tailwind.preset.ts`, and no `hsl()` wrapper.** This section originally called for a `packages/ds/tailwind.preset.ts` and `hsl(var(--...))` color syntax — both v3-era Tailwind conventions. Verified directly against the installed `tailwindcss@4.3.3`: v4's config model is CSS-first (`@theme` blocks + `@import`), and JS/TS "presets" are only a legacy compatibility path via `@config`, not the idiomatic v4 approach. Style Dictionary's actual output (`build/css/tokens.css`) also emits colors as bare hex (`--color-intent-primary-base: #006da3`), not H/S/L triplets, so `hsl(var(--...))` would be invalid CSS against these vars regardless. The real artifact is `packages/ds/src/theme.css`: it `@import`s the three built token CSS files (bringing every tier — primitives/semantic/component/density — into the cascade as plain custom properties) and defines a `@theme` block that aliases only the `color-intent-*` and `color-response-*` semantic tokens into Tailwind's color namespace (`bg-primary`, `text-critical-strong`, etc). Every other tier is deliberately left unaliased — components reference those vars directly via arbitrary values (`h-[var(--component-button-min-height)]`), consistent with the primitives → semantic → component tiering in §1.2. Verified end-to-end with `@tailwindcss/cli`: utility classes resolve through the full var chain to the correct hex value, the `[data-theme="dark"]` and `[data-density="..."]` override blocks pass through untouched, and `pnpm --filter ds theme:check` compiles the file standalone as a smoke test.

**Elevation & Shadows utility classes — added 2026-08-24, first use of Tailwind v4's `@utility` directive in this codebase.** `tokens.json`'s Elevation & Shadows primitives (the full 8-level scale from the Styles library, verified directly against its own effect styles) had never been consumed by any component before SegmentedControl needed two of them (`Carved`, `Settled`). Rather than compose the multi-var, comma-separated `box-shadow` value inline in every consumer, `theme.css` now defines all 8 levels as `shadow-elevation-*` `@utility` classes (`@utility`, not `@apply` — these set one raw CSS property from custom properties, not a combination of other utility classes), backed by a new `semantic.elevation.*` token bucket. Only 2 of the 8 levels are consumed yet; the other 6 are built out now as a complete, reusable set for Card/Dialog/etc. to pick up later. Full verification writeup in `HAND_ADDED_TOKENS.md`'s `semantic.elevation` entry.

**Pipeline history:** the original plan locked in "free Figma community plugin only, no Tokens Studio" to keep the showcase reproducible on a free plan. Several free plugins produced structurally broken exports (double-encoded JSON, no real aliasing, ambiguous `"value"`-as-token-name collisions, inconsistent unit handling), which is what motivated purchasing Tokens Studio Pro and doing a one-time, non-reproducible export instead — an explicit, conscious tradeoff for this proof-of-concept, not a reproducibility guarantee reviewers can expect to re-run from a fresh Figma file.

**Dark mode readiness without dark mode work:** The key decisions that make later dark-mode trivial are (a) the primitive/semantic split in §1.3, (b) CSS-var-based color references in Tailwind theme, and (c) component code that never hardcodes color values. The partial dark mode already authored in Figma is handled by the sparse `[data-theme="dark"]` block — only tokens with actual overrides appear there. As of the Tokens Studio export, that's exactly 12 tokens, all under `layout.backgroundColor.*`; no component currently references that part of the color tree, so dark mode is wired end-to-end but not yet visibly different from light for any shipped component.

### 1.2 Figma Hygiene: Layer & Prop Naming to Streamline Import

You'll normalize each of the three Figma libraries once, before its first export. Subsequent edits inherit the naming.

**In the Styles library (tokens):**

- **Variable names** — slash-delimited (Figma's native group separator), semantic-first: `color/bg/primary`, `color/text/muted`, `density/padding/sm`, `density/height/md`. Avoid spaces, ampersands, or marketing names. Style Dictionary transforms slashes to dashes in CSS output (`--color-bg-primary`, `--density-padding-sm`).
- **Collections & modes:**
  - `primitives` collection — single default mode. Raw values only: color scales (`blue.500`, `gray.100`), size, space, border-radius, font, and shadow primitives. Nothing in this collection is consumed directly by components.
  - `semantic` collection — single default mode. Role-based aliases onto primitives (`content.text-color.default` → `{primitives.color.neutral.100}`, typography and spacing roles, etc.). Not tied to any single component.
  - `component` collection — single default mode. Component-specific aliases onto semantic (and occasionally primitive) tokens, one group per component (`button.background-color.primary.default`, `card.border-radius`, etc.). Components should reference `component` tokens first, falling back to `semantic` where no component-specific override exists.
  - `color` collection — modes: `light` (primary), `dark`. Color-only tokens, referenced by the `semantic`/`component` tiers wherever a value needs to flip with the theme.
  - `density` collection — modes: `roomy` (default), `condensed`. Sizing/spacing-only tokens, referenced by the `semantic`/`component` tiers wherever a value needs to flip with density.
  - Mode names are lowercase bare words (no "Mode" suffix) so they map cleanly to `data-theme` and `data-density` attribute values.
- **Three-tier alias chain** — `primitives` → `semantic` → `component`. This is the load-bearing decision that makes future dark mode, density theming, and rebranding trivial: swapping a primitive or a `color`/`density` mode value cascades up through semantic and component aliases without touching component code.
- **Density values** — unitless numbers in Figma (px unit attached by Style Dictionary transform).

**In the Assets library, Icons page:**

- **Icon names** — kebab-case (`chevron-right`, `map-pin`). SVGR will PascalCase these on export (`ChevronRight`, `MapPin`).
- **Category frames** — icons are grouped into named frames/groups per category (e.g. a `Navigation` frame containing `chevron-right`, `chevron-left`, ...). The frame/group name becomes each icon's `category` in the generated manifest (§1.3) — keep frame names short, PascalCase or Title Case, one level deep. Don't nest category frames inside other category frames.
- **Single frame per icon** — uniform sizing (e.g. 24×24), centered, stroke-only or fill-only consistently. SVGR doesn't fix inconsistent source.
- **Use `currentColor`** — set icon strokes/fills to a single color in Figma and ensure the exported SVG uses `currentColor`. If Figma is exporting hex codes, run a post-export SVGO pass that swaps fills to `currentColor` (configured in SVGR).
- **No background frames** — flatten away wrapper rectangles before export, or the SVG will have a transparent square that breaks vertical alignment.

**In the Assets library, Illustrations page:**

- **Illustration names** — component names are `Illustrations/<Title Case Name>` (e.g. `Illustrations/Living Debt Free`) as currently authored, not kebab-case. The export script strips the `Illustrations/` prefix and kebab-cases the rest (`living-debt-free`); SVGR PascalCases from there, same as icons.
- **Multicolor is intentional** — do not flatten to `currentColor`; the SVGO/SVGR pipeline for this package skips the color-stripping pass entirely and preserves authored fills/strokes as-is. Confirmed via export: each illustration uses 7-8 distinct hex fills.
- **Uniform 104×104 frame** — confirmed via export: all 22 illustrations are 104×104 (one off-by-one at 105×104, treated as noise). Still flatten away background/wrapper frames before export.
- **Category frames optional** — grouping isn't required on this page; if present, it's ignored by the export pipeline (illustrations are few enough not to need a catalog taxonomy yet).

**Known inconsistencies as of the 2026-08-04 MCP export** (source of truth: the Figma file, not this list — re-check on every re-export):

- Icons use hardcoded `fill="#006DA3"`, not `currentColor` — the SVGO `currentColor` pass in `packages/icons/svgr.config.cjs` is load-bearing, not a defensive no-op.
- Not every icon is actually single-color: `trash`, `notice-error`, `data-vis-loss` use red `#CB0B31`; `checkmark-circle`/`data-vis-gain` use green `#247E58`; `notice-warning` uses orange `#D13805`; `notice-info` uses `#4B4D4E`; `rating-star-full`/`rating-star-half` use gold `#C08D16`; `rating-star-empty` uses gray `#7D8082` — these are intentional semantic accent colors, not the neutral default. The SVGR `replaceAttrValues` transform targets only the literal `#006DA3` string, leaving every other hex value untouched, so these icons keep their authored color instead of being flattened to `currentColor`.
- ~~`object-substract.svg` / `object_subtract.svg` naming drift~~ — fixed in Figma same day: renamed to `object-subtract` (24×24) and `object_subtract-sm` (16×16, underscore kept as authored).
- ~~`data-vis-heirarchy.svg` typo~~ — fixed in Figma same day: renamed to `data-vis-hierarchy`.
- ~~`building-institution.svg` exported at 26×26~~ — fixed in Figma same day: re-exports at 24×24, matching every other standard icon.

**In the Components library:**

- **Component property names must equal code prop names** — `intent`, `size`, `disabled`, not `Style`, `Size/Type`, `State`. Variant _values_ must match too: `primary`, `ghost`, `sm`, `md` — not `Primary Button`, `Default`.
- **Slot/anatomy naming** — for compound components (Dialog, DropdownMenu, Card, etc.), Figma layers should match Radix anatomy: `Trigger`, `Content`, `Item`, `Separator`, `Label`, `Header`, `Body`, `Footer`. This makes the Figma file readable as a spec for the code.
- **Reference icons by name** — components that contain icons should reference the Icons library by name (`map-pin`), not contain inline SVG, so code can swap to `<MapPin />` deterministically.

**Deviation from plan (2026-08-13): Figma prop/variant naming stays Title-Case; only code translates it.** The rule above ("component property names must equal code prop names") was reversed after actually building against it — see `docs/FIGMA_COMPONENT_AUDIT.md`'s "Recommended fixes — Button (worked example), Issue 1" for the full reasoning. Forcing Figma properties into camelCase (`showLabel` instead of `Show Label`) trades a code-side convenience for real cognitive load on less-technical design staff, who'd have to author and read camelCase in the properties panel instead of natural prose. **Figma keeps human-readable Title-Case names and Title-Case variant values** (`Show Label`, `Size=Large/Small`, etc.); the camelCase/lowercase translation happens once per component, by hand, when that component is actually built in code — there's no automated Figma → component codegen in this project (unlike `tokens`/`icons`, which have real export pipelines), so there's nothing to wire a live conversion into. The "State=Idle/Hover" pseudo-class-as-variant pattern (Button, Segmented Control, Tabs) gets the same treatment for a different reason: it can't be removed from Figma at all (three approaches were tried and hit real Figma limitations, documented in full in the audit doc's Issue 3) — `State` stays permanently visible in Figma and is simply never implemented as a prop in code; hover is always CSS `hover:`, never data-driven. The slot/anatomy-naming and icon-referencing rules above are unaffected by this deviation — only the specific "prop names must equal code prop names" clause is reversed.

**Size-scale prop value translation (2026-08-14):** The Title-Case-stays-in-Figma deviation above still leaves an open question for any component with an ordinal size scale (Avatar's `Size=X-small/Small/Default/Large/X-large/XX-large`, and future components with similar scales) — hand-translating each one is unnecessary judgment calls when the scale itself is fully mechanical. Use this fixed lookup table, matching Tailwind's own T-shirt naming convention, every time a Figma size variant is translated to a code prop value:

| Figma value             | Code value |
| ----------------------- | ---------- |
| XXX-small               | `3xs`      |
| XX-small                | `2xs`      |
| X-small                 | `xs`       |
| Small                   | `sm`       |
| Default / Medium / Base | `md`       |
| Large                   | `lg`       |
| X-large                 | `xl`       |
| XX-large                | `2xl`      |
| XXX-large               | `3xl`      |

Rule: strip `X-`/`XX-`/`XXX-` prefixes to a numeric multiplier prepended to the base word's Tailwind abbreviation (`small`→`sm`, `large`→`lg`); the unqualified middle value always becomes `md` regardless of whether Figma calls it "Default," "Medium," or "Base." This table applies only to ordinal size scales — non-ordinal domain variants (Avatar's `User=Associate/Entity`, Button's `State=Idle/Hover`, `Intent=Default/Destructive`) have no scale to mechanize and stay a deliberate per-component naming call, per the deviation note above.

### 1.3 Icons Pipeline (Figma "Assets" library, Icons page → code)

The Icons page gets its own package (`packages/icons`) and its own one-way pipeline. Export can go through the Figma Dev Mode MCP server (`mcp__figma__get_figma_data` + `download_figma_images` — available on this Pro plan with a Full seat) instead of a manual batch export, since the icons are all components on a single page.

1. **Export SVGs from Figma** — traverse the Icons page's category frames/groups (via MCP `get_figma_data`, or Figma's built-in batch export / the free **SVG Export** community plugin as a fallback), recording each icon's parent frame/group name as its category. Download SVGs into `packages/icons/source/*.svg` (flat — category isn't a folder split, see §1.2).
2. **Generate the category manifest** — a small script (run as part of `pnpm icons:build`, before SVGR) writes `packages/icons/src/generated/manifest.ts`: a `Record<string, { category: string }>` keyed by kebab-case icon name, sourced from the frame/group names captured in step 1. This is the only place category information is persisted — inspect the real MCP node tree first (frame nesting, naming) before writing the extraction logic, same lesson as the token pipeline: verify the export's actual shape, don't trust the docs.
3. **Transform with SVGR** — `svgr.config.cjs` configures:
   - Output to `packages/icons/src/generated/*.tsx`, one React component per icon, PascalCased.
   - Replace hardcoded fills/strokes with `currentColor` (via the `replaceAttrValues` config or an SVGO plugin) so icons inherit text color.
   - Spread incoming props to the root `<svg>` so consumers can pass `className`, `width`, `aria-label`, etc.
   - Type the props as `SVGProps<SVGSVGElement>` with an optional `size` shorthand.
4. **Barrel export** — `packages/icons/src/index.ts` re-exports every generated icon as a named export: `export { ChevronRight, MapPin, ... }`, plus the generated `manifest`. Tree-shaking handles dead-code elimination, so consumers only pay for what they import.
5. **Optional `<Icon name="..." />` wrapper** — a runtime-string API for cases where icon choice is data-driven (e.g. `location.category === 'cafe' ? 'coffee' : 'shop'`). Implemented as a lookup map over named exports. Skip if not needed.
6. **Refresh loop** — `pnpm icons:build` re-runs the manifest generator then SVGR. Two-step manual sync (`export from Figma` → `pnpm icons:build`).

**Why a separate package** (not bundled into `packages/ds`):

- Mirrors the Figma library split — clean conceptual story.
- The locator can import icons without dragging in the DS bundle.
- The icon pipeline (SVGR + SVGO) has no overlap with the DS build, so isolating it keeps `packages/ds`'s build config simple.

**Implementation notes / deviations from spec (2026-08-04 build), TODO for later:**

- **No `size` shorthand on generated components.** Step 3 above calls for one; it isn't implemented. Baking a dynamic `size` prop into SVGR's output requires a custom JS template (SVGR's template API builds the `<svg>` JSX from the source file's own static attributes, so merging in a runtime `size` variable means hand-rolling the AST rather than using SVGR's default template) — disproportionate complexity for 107 generated files when consumers can already do `<ChevronRight width={16} height={16} />` via prop spreading. TODO: if the locator (or a future `<Icon name="..." />` wrapper, step 5) ends up needing `size` in practice, implement it there instead of in every generated file.
- **Generated components use `forwardRef`, not React 19's ref-as-prop.** `svgr.config.cjs` sets `ref: true` for ref-forwarding support; SVGR's TypeScript template (last released 8.1.0, predates React 19's stable release) only knows how to implement that via `React.forwardRef`. This still works fine on React 19 (`forwardRef` isn't broken, just discouraged for new code per the React docs, which note a future release may deprecate it) — it's SVGR's default, not a deliberate choice. TODO: if SVGR ships React 19-native output, or if `forwardRef`'s deprecation becomes real, swap in a custom template using `function Icon({ ref, ...props })` instead. Low priority — no functional issue today. (Figma "Assets" library, Illustrations page → code)

The Illustrations page gets its own package (`packages/illustrations`), sibling to `packages/icons`, with a pipeline that mirrors the icons pipeline minus the color-normalization step:

1. **Export SVGs from Figma** — same mechanism as icons (MCP `get_figma_data`/`download_figma_images`, or manual batch export), targeting the Illustrations page instead. Category grouping is not extracted (§1.2 — optional and ignored on this page). Drop into `packages/illustrations/source/*.svg`.
2. **Transform with SVGR** — a separate `svgr.config.cjs` (not shared with `packages/icons`):
   - Output to `packages/illustrations/src/generated/*.tsx`, one React component per illustration, PascalCased.
   - **No `currentColor` replacement pass** — fills/strokes are left exactly as authored, since illustrations are intentionally multicolor.
   - Spread incoming props to the root `<svg>` (className, width/height) but do not add a `size` shorthand — illustrations aren't meant to be icon-scale.
3. **Barrel export** — `packages/illustrations/src/index.ts` re-exports every generated illustration as a named export: `export { EmptyState, OnboardingWelcome, ... }`.
4. **Refresh loop** — `pnpm illustrations:build` re-runs SVGR for this package. Same two-step manual sync as icons.

**Why a separate package from `packages/icons`** (not one shared assets package):

- The two asset types have genuinely different transform rules (currentColor coercion vs. none) — sharing one SVGR config would mean branching logic inside it instead of two simple configs.
- Consumers rarely need both at once; the locator can pull `packages/illustrations` for an empty state without any icon-specific tooling coming along.
- Keeps the "one Figma concern, one package" story intact even though both pages live in the same Figma library file.

### 1.4 Density System

The design system supports two density modes — **Roomy** (default) and **Condensed** — as an orthogonal dimension to color theming. Density controls the physical scale of components (padding, height, gap, icon size within components). It does not affect color, radius, font family, or font weight.

**Architecture:** CSS `data-density` attribute on ancestor elements. CSS custom properties cascade from the nearest `data-density` ancestor, so the full React component tree needs no changes for inheritance.

```
<html data-density="roomy">          ← global default
  …
  <aside data-density="condensed">   ← per-element override
    <List>…</List>                   ← inherits condensed from aside
    <Button size="sm" />             ← inherits condensed from aside
  </aside>
```

**Global default:** `<html data-density="roomy">` is intended to be set both in `apps/locator/index.html` and by Storybook. **Correction (2026-08-21):** this wasn't actually true yet as of building Dialog — `apps/locator` is still an empty skeleton with no `index.html` at all (per `CLAUDE.md`), and Storybook's `preview.tsx` only set `data-density` on its own per-story decorator `<div>`, never on the real `<html>`. That gap is invisible for normal, non-portal components (whatever wraps a story still cascades to them normally), but Radix Portal-rendered content (`Dialog.Content`, `SelectInput.Content`, later Popover/Tooltip) renders to `document.body`, escaping that decorator div entirely — with no `<html>`-level fallback and no explicit `density` prop of its own, a portal component has zero `data-density` ancestor anywhere, so every density-scoped CSS var it uses (including ones on nested children, e.g. a `Button` inside `Dialog.Footer`) silently fails to resolve. Fixed by (1) `preview.tsx`'s decorator now also mirrors the toolbar's density live onto `document.documentElement`, restoring the intended global-fallback behavior for Storybook, and (2) every portal component's own `Content`-part `density` prop now defaults to `'roomy'` rather than staying `undefined` (`Dialog.Content`, `SelectInput.Content`) — a safety net that holds regardless of whether a consuming environment remembers the global `<html>` attribute, since `apps/locator/index.html` doesn't exist yet to verify either way. Components never need to know the default in the common case — they just read CSS vars, which resolve as long as **some** `data-density` ancestor exists — but portal components can't rely on that assumption passively, hence the explicit per-component default.

**Component `density` prop:** Every component with density-sensitive sizing accepts:

```ts
density?: 'roomy' | 'condensed'
```

When provided, the component sets `data-density={density}` on its root element. When omitted, the component inherits from its ancestor via CSS cascade.

**cva integration:** Density does **not** drive cva variants (that would require JS density awareness). Instead, density is purely CSS-var-driven. The `size` cva variant (`sm | md | lg`) selects which CSS vars a component references; the density mode controls what those vars resolve to:

```ts
const buttonVariants = cva({
  base: 'inline-flex items-center',
  variants: {
    size: {
      sm: 'h-[var(--density-height-sm)] px-[var(--density-padding-sm)] gap-[var(--density-gap-sm)]',
      md: 'h-[var(--density-height-md)] px-[var(--density-padding-md)] gap-[var(--density-gap-md)]',
    },
  },
});
```

**Portal caveat:** Radix overlays (Dialog, Tooltip, Popover) render into a portal outside the DOM tree, breaking CSS cascade inheritance. Pass the `density` prop explicitly to these components — the component sets `data-density` directly on the portal content root.

**`useDensity` hook (optional):** A thin hook reading the nearest `data-density` ancestor via attribute walk. Only needed in rare cases where JS must know the current density value (e.g., conditionally rendering different icon sizes). Not required for core functionality.

### 1.5 Future: Code as Source of Truth, Figma as Output

When the direction reverses later, the pipeline reverses by updating Figma Variables directly via a plugin that supports bidirectional variable sync (several free and paid options exist). To prepare now without doing the work:

- Keep `packages/tokens/source/` the only token input — never edit CSS vars by hand.
- Treat the JSON schema as a contract; document field shapes in `packages/tokens/README.md`.
- Avoid platform-specific token names in Figma (no `xs`, `2xl` Tailwind arbitraries) so the JSON stays platform-neutral.

This means the eventual flip is a workflow change, not a code rewrite. (Icons stay one-directional Figma → code — SVGs are visual source material.)

**Authoring conventions for every component:**

- Forward refs — using React 19's native `ref`-as-prop (destructure `ref` directly from the function component's props), not `React.forwardRef`. The one exception is `packages/icons`' generated components, where SVGR's TypeScript template predates React 19 and only knows how to emit ref forwarding via `React.forwardRef` (see §1.3 implementation notes) — that's a codegen tooling constraint scoped to that package, not a hand-written-component convention.
- Accept `className` + `asChild` where meaningful.
- Accept `density?: 'roomy' | 'condensed'`; when provided, set `data-density` on the component root.
- Variant API via `cva` exported alongside the component for product-level extension. The `cva(...)` call is declared before every component function in the file (Avatar/Label's original ordering) — TextInput briefly inverted this (Root, a component that doesn't even use the variants, declared first) before being caught and reverted; the file should read variants-then-consumers, not interleaved by whichever part was written first.
- All sizing (padding, height, gap) uses CSS vars from the density system — no hardcoded values.
- Compound components use dot-notation exports (`Card.Root`, `Dialog.Trigger`) to mirror Radix anatomy and Figma slot naming.
- Each component exports its props type for product consumption. Props types/interfaces live in a dedicated `<Name>.types.ts` file, imported into `<Name>.tsx` — types are never defined inline in the component file.
- **Comments stay terse — one or two lines on the non-obvious WHY, never a paragraph.** Well-named identifiers already say what the code does; a comment earns its place only when it captures a hidden constraint, a Figma/CSS-mechanism nuance, or a "this looks right but isn't" trap a future reader would otherwise re-derive. Established 2026-08-17 after repeatedly trimming multi-paragraph comments back down during the Button and Link builds — default to terse on the first draft, don't wait for a correction.
- **No hardcoded color, spacing, or radius values** — always reference Tailwind classes backed by tokens, so dark mode lights up later without component edits. This includes gaps and icon sizes inside compound sub-parts, not just the obvious top-level padding — SelectInput.Option's padding/gap/icon-size were hand-authored as plain Tailwind spacing scale values in a first pass and had to be swapped for the same density tokens the sibling Trigger already used, once the lack of density response was caught.
- **When two CSS rules driven by different data-attributes/pseudo-classes can compete for the same element (e.g. a "highlighted" state vs. a "selected" state that can both be true at once), prefer adding a genuinely-true extra condition to bump one rule's specificity over the other rather than reaching for `!important`.** SelectInput's checked/highlighted/hover chain resolved this way: since real pointer hover always also sets Radix's `data-highlighted`, folding that same attribute into the hover-specific selector (`[data-state=checked][data-highlighted]:hover`) pushed it strictly above the two-condition "reassert on any highlight" rule, with no `!important` and no dependence on Tailwind's internal utility-generation order. Only reach for `!important` once no such natural extra condition exists — and even then, ask the user before adding it rather than reaching for it unilaterally, since it's a blunt tool that can bite unrelated overrides later.
- **Portal-rendered components (Dialog, Popover, Tooltip) set `data-density` on their content root, and their `density` prop defaults to `'roomy'` rather than staying `undefined`.** Established 2026-08-21 on Dialog/SelectInput (full writeup in §1.4) — a Portal escapes the ancestor DOM tree entirely, landing in `document.body`, so a portal component can't passively rely on inheriting from _some_ ambient `data-density` ancestor the way every non-portal component safely can; without its own concrete default, an un-set `density` prop leaves the whole portaled subtree (including nested children like a `Button` inside `Dialog.Footer`) with no `data-density` ancestor at all, silently failing every density-scoped CSS var it uses.
- **Shared-but-non-public component logic (not tied to one Figma component's identity) lives in `src/internal/`, not `src/components/` or `src/utils/`.** Established 2026-08-16 with `internal/GroupFieldList.tsx`, the bordered-options-slot shell shared by ChecklistGroup.Group and RadioGroup.Group — it isn't itself a Figma-authored component (unlike everything in `components/`, which maps 1:1 to a real Figma node) and isn't barrel-exported from `index.ts` (unlike everything in `utils/`, which is plain non-JSX helper functions like `cn`). Consumers reach `ChecklistGroup.Group`/`RadioGroup.Group`, never `GroupFieldList` directly.
- **When a visual state (disabled, checked, etc.) can be set either on a component itself or inherited from an ancestor context (e.g. a whole `RadioGroup.Root` disabled at once, not just one `RadioGroup.Item`), style off the rendered DOM's data-attribute via CSS, not a JS-computed prop variant.** A `cva` variant keyed only off the component's own `disabled` prop misses the ancestor-disabled case entirely, since a consumer disabling a whole group wouldn't repeat `disabled` on every item — but Radix propagates `data-disabled` to each item's DOM regardless of which source triggered it. Established 2026-08-16 on `RadioButton`: the ring/indicator were already `data-[disabled]:`-driven and correct, but the label text and cursor were still JS-prop-driven and silently missed group-level disabling until caught in review. Fixed with `peer`/`peer-data-[disabled]:` for a following sibling (the label `<span>`, which follows the Radix `Item` in DOM order) and `has-[[data-disabled]]:` for an ancestor (the wrapping `<label>`) — two different CSS mechanisms for two different structural relationships, not interchangeable: `peer-*` only reaches a later sibling reacting to the peer's own state; `has-*` is the real `:has()` selector, letting a parent react to a descendant.
- **Before hand-adding a `borderWidth` token because a component's own `component.<name>` bucket has no entry for it, check whether it's already bound in Figma to a semantic-tier token (`surface.borderWidth`, etc.) rather than assuming it's unbound.** The Figma MCP server's `get_figma_data` output resolves bound _fills_ into named, deduped variable references (the `fill_xxx` entries in `GLOBAL_VARS`), but does not surface the same provenance for `strokeWeight` — a bound stroke and a coincidentally-identical literal render identically in that tool's output (a bare `strokeWeight: 1px`), so an absent `component.<name>.borderWidth` alias in `source/tokens.json` only proves the _export_ didn't carry a per-component alias through, not that Figma has no Variable at all. Established 2026-08-17 on `Button`: `component.button.borderWidth` was hand-added assuming the stroke was a plain unbound literal, documented as a Figma to-do ("author a `borderWidth` Variable") — user correction revealed it was already bound to `surface/borderWidth` the whole time. Fixed by aliasing to `{surface.borderWidth}` (tracing the real binding) instead of reaching straight to a primitive-adjacent alias, and the "to close in Figma" note was removed since there was nothing to close there. When a hand-add's only evidence is "this component's own token bucket has no entry," check the relevant semantic-tier bucket (`surface.*`, `control.*`, etc.) for a matching value before writing the Figma to-do — the gap is often in the export's per-component aliasing, not the authoring.
- **When choosing which existing semantic-tier token a new component-tier alias should point to, resolve every real candidate's actual hex/value and diff each against the literal fill the Figma fetch already reported for that exact state — never pick by name-pattern-matching against what a sibling component calls its "equivalent" token.** This is a distinct mistake from the `borderWidth` case above: there, nothing existed for that path and a value had to be sourced. Here, both candidates were already real, Figma-authored semantic tokens sitting in the export — the error was purely picking the wrong one of two legitimate options, not inventing anything. Established 2026-08-18 on `Tabs`: `component.tab.textColor.disabled` was aliased to `intent.disabled.text` purely because that's the name TextInput/RadioButton/Checkbox use for their own disabled-text token — but the fetch's own `GLOBAL_VARS` had already reported the Disabled variant's text fill as a distinct, named hex (`#7D8082`) that `intent.disabled.text` (`#4B4D4E`) doesn't match; the correct, already-authored token (`control.action.color.disabled.secondary` → `intent.disabled.base`) was sitting in the same fetch response the whole time, just under a name that didn't pattern-match the sibling-component convention. The fix is a verification step, not "trust the MCP output more" (that data was already correct and present): after picking a candidate alias — hand-added leaf or not — always resolve it and compare the resulting hex against the specific state's literal fill before writing it to `source/tokens.json`.
- **The `borderWidth`/`strokeWeight` MCP-surfacing gap above isn't stroke-specific — spacing/padding has the same blind spot, and a fetch's numbers reflect whichever density mode the Figma file happens to be showing at that moment, not a fixed value.** Established 2026-08-18 on `Tabs`: an early fetch of 158:4621 returned `padding: 4px 16px` on the Button instance nested in `Tab`, read as "the" padding value and hand-added as a flat, non-density alias — which is why Tab rendered at a constant height regardless of `data-density` instead of the 48px/32px roomy/condensed target. A later re-fetch of the same node, with the file on a different mode, returned `padding: 12px 20px` — an exact match for `control.action.padding.block`/`.inline`, the same density-aware bucket `Button`'s own padding already uses. Two lessons: (1) a `get_figma_data` fetch is a snapshot of the file's _current_ mode selection, not a canonical value — a single fetch can't tell you whether a dimension is flat or density-varying, only what it resolves to in whatever mode was active; (2) before hand-adding _any_ dimension (not just `borderWidth`) as flat because only one fetch's number was seen, sanity-check it against a sibling component's own known density pair (Button's 12px/8px padding, 24px/16px line-height) — a plausible-looking number that happens to land near an established density step is a signal to re-fetch and check for mode-reactivity before writing it down as fixed.
- **A component-tier size/spacing value's semantic-tier answer is the `fixed`/`dynamic` `sizing`/`spacing` scale, not a bare `primitives.ref.size.*`/`ref.space.*` value.** These scales are nested under the `density` collection's `roomy`/`condensed` modes structurally, but the `fixed` side is density-_invariant_ by definition (only `dynamic` actually differs between modes) — so for a non-density-reactive value, `{spacing.fixed.small}`/`{sizing.fixed.small}` is the real semantic-tier reference, the same tier `content.size.*`/`control.borderWidth.*` already occupy for type/border-width. Established 2026-08-19 on `Tag`, after a first pass wrongly concluded no semantic spacing tier existed at all (based on `component.button.gap`'s own precedent of aliasing straight to `ref.size.03`) — corrected directly by the user. `HAND_ADDED_TOKENS.md` carries a TODO to audit the other pre-existing `gap` hand-adds (Button, Checkbox, ChecklistGroup, RadioGroup, Radio) against this same distinction.
- **Standing rule, generalized from the `borderWidth`/text-color/spacing cases above (2026-08-23): when hand-adding any `component.*` token, always look for an existing `semantic`-tier candidate first and alias to it — never write a `component.*` token that aliases straight to a `primitives.ref.*` value, under any circumstance, even when no semantic candidate is an exact value match yet.** If a component's own value doesn't match any existing semantic step closely enough to reuse, keep it a plain literal and flag the gap in `HAND_ADDED_TOKENS.md` rather than reaching past the semantic tier down to a primitive — a literal is an honest "nothing here yet"; a primitive-tier alias looks like a resolved answer but silently breaks the tiering's whole purpose (rebranding/theming/density changes no longer propagate through a token this component references). This is the rule the `borderWidth` (2026-08-17), text-color (2026-08-18), and spacing/sizing (2026-08-19) bullets above were each independently re-deriving case by case — those stay as the historical record of why it matters, this bullet is the one to actually follow going forward. Chip's own `borderRadius` lived out this exact arc within the same session: the initial fetch read `3px`, matching no existing step (`control.borderRadius` is 4px), so it shipped as a literal per this rule rather than reaching for the nearest primitive; days later a Figma re-fetch found the authored value had changed to a flat `2px` — an exact match for `{borderRadius.subtle}` — and the literal was repointed onto that real semantic step (see the dated Chip note below and `HAND_ADDED_TOKENS.md`'s `component.chip` entry). The literal wasn't a dead end, it was the correct holding state until a real match existed.
- **A prop whose doc is meant to read identically across multiple components' contracts uses a shared, named type as the single source of that doc, not a comment re-typed per component.** `AriaLabelProp` (`packages/ds/src/utils/a11y-props.ts`) is the first instance, not a special case scoped to accessibility — any prop genuinely shared verbatim across components' `.types.ts` files follows the same shape, in whichever `utils/` file its subject matter fits (an a11y-specific file doesn't have to host a non-a11y prop's shared type). A component using the generic wording extends the shared type directly — `Omit<ComponentProps<'el'>, '<prop-name>'>` first, so the shared type is the only contributor of that key and the hover doc isn't ambiguous. A component with a genuinely more specific scenario (e.g. `CloseButton`'s `aria-label` doc, "multiple dismissible things on one page," vs. `AriaLabelProp`'s generic wording) defines its own local `<Component><PropName>Prop` type with its own doc instead of redeclaring the property inline inside the main props interface — but never extends both the shared type and a local override together, since two interfaces contributing the same key makes TypeScript's resolved hover doc ambiguous/tool-dependent. Established 2026-08-20 on `Button`/`CloseButton`'s `aria-label`.

**Label — built 2026-08-14, first `packages/ds` component after Avatar.** Confirms the flat-primitive listing above (no compound sub-parts needed) and wraps Radix's `Label.Root` directly (`radix-ui`'s `Label` export — same package, not a new dependency), which gets the native `htmlFor` association plus Radix's click-without-selecting-text fix for free. Same reasoning as Avatar's fixed size scale.

**TextInput — built 2026-08-14, immediately after Label.** Ships as the compound Root/Label/Field/Microcopy API scoped as an open question in RESUME_NOTES ("TextInput.Label/.Field/.Microcopy composed with flexbox — same Root/Icon/Label-style compound pattern as Button and Avatar"), and confirms it: `TextInput.Label` is the standalone `Label` component itself (not a re-implementation) since Figma's TextInput compound (122:1502) nests a real "Input Label" instance and `Label` already covers the full requirement/error surface needed. `TextInput.Microcopy` reuses `component-label-*` tokens rather than adding `component-text-input-microcopy-*` ones — Figma's Microcopy text run shares Label's exact 14px/400 default style and error red.

- **`component-text-input-*` tokens were mostly missing and got hand-added**, same pattern as `component-avatar-*` for Avatar. Only the `default` state (background/border/text-color, border-radius/width, input-value font-size/weight) existed in the Figma export; `error`/`active`(focus)/`disabled` had real authored values in Figma (confirmed via direct re-fetch of 121:1315/121:1322) but no tokens. Added `borderColor.{error,active,disabled}`, `backgroundColor.disabled`, and `textColor.disabled` to `packages/tokens/source/tokens.json`'s `component.textInput`, aliased to already-existing semantic tokens (`response.critical.base`, `control.color.accent.active`, `control.color.disabled.secondary`, `intent.disabled.text`) — no new primitives, every hex value confirmed to match the Figma fetch exactly after rebuild.
- **`State=Idle/Hover`-style pseudo-class handling extends to Figma's `Active` (focus) state**: never a prop, always `focus-within:` CSS on the Field wrapper, per the same precedent as Button/SegmentedControl's `State` axis (`docs/FIGMA_COMPONENT_AUDIT.md`). `error`, native `disabled`, and native `readOnly` are real props; `TextInput.Field` derives one visual `state` from them with `disabled` taking precedence (Figma never defines Disabled+Error or Disabled+Read-Only combinations).
- **Focus renders as an inset `box-shadow`, not a wider `border`.** Figma's Active state is a 4px border vs. 1px default; naively swapping `border-[length:...]` on focus grows the real border and eats into the content box even under `box-sizing: border-box`, nudging icon/text inward. Border-width now stays fixed at the default token value in every state; focus adds a color change plus an inset shadow sized via `calc(var(--semantic-control-border-width-active) - var(--component-text-input-border-width))` — token-derived, not a hardcoded "3px" — so field dimensions never shift between states.
- **A new density-mode token pair closes a real gap between the min-height and padding tokens.** `--density-control-input-small-min-height` (48px roomy / 32px condensed) and `--density-control-input-padding-block` (12px / 8px) are both correctly density-aware, but line-height is deliberately _not_ density-scoped per §1.4 ("density controls padding, height, gap, icon size... not font family or weight") — so the input-value text sat at a fixed 24px line-height in both modes, and `8+8+24=40px` overshot the 32px condensed target (`12+12+24=48px` happened to match roomy exactly, which is why the gap wasn't obvious at first). Fix: added `density.<mode>.control.input.small.lineHeight` (`{ref.size.07}`=24px roomy, `{ref.size.05}`=16px condensed — both pre-existing primitive scale steps, no new primitives), then aliased it into `component.textInput.inputValue.lineHeight` alongside the pre-existing `fontSize`/`fontWeight` siblings there, rather than having the component reach past its own tier straight into `density`. Confirmed via `tokens-json-review` and a rebuild that both densities now hit their exact pixel target.

**Fix (2026-08-16, separate branch from the four components above): `RadioGroup.Root`/`ChecklistGroup.Root` were stretching their `Group` child to fill the full container width instead of hugging content.** Caught by the user reviewing the merged Storybook stories, not during the original builds. But `display: grid` alone doesn't shrink-wrap a block-level container's own _outer_ box — without `w-fit`, `Root` still filled 100% of its parent's width regardless of the column definition, since a block box's `width: auto` means "fill available inline space," not "shrink to content." - **Consumers still override to fill a container with no new prop** — `tailwind-merge` cleanly drops `w-fit` in favor of an explicit width passed via the existing `className` (e.g. `w-72`), confirmed directly (`twMerge('... w-fit ...', 'w-72')` → `w-fit` removed) rather than assumed. Fixed by subtracting the border width from the padding-block calc — `py-[calc(var(--component-button-padding-block)-var(--component-button-border-width))]` — rather than shrinking the line-height (which would distort the text's actual vertical rhythm away from Figma's authored 24px/16px value) or the min-height token itself (shared with `minWidth`/other consumers). Also surfaced that Button's border width had no `component.button`-scoped token at all (hardcoded `1px` in the component) despite genuinely being bound in Figma to `surface/borderWidth` — the export just never carried that binding through to a per-component alias. Added `component.button.borderWidth` → `{surface.borderWidth}`, tracing the real binding rather than reaching past it, so the padding calc and the border declaration reference the same var and can't drift apart — see `HAND_ADDED_TOKENS.md`.
- **Fix (2026-08-21): icon-only buttons (`showLabel={false}`) weren't rendering as a square, despite `min-width`/`min-height` being numerically equal.** Both bugs above fixed _height_ against a min-height floor, but icon-only _width_ was still purely content-driven (`icon + padding-inline×2 + border×2`) — `min-width` was a floor, not a fixed value, so once content exceeded it (58px roomy / 46px condensed vs. a 48px/32px target) the floor never actually bound. A second, less obvious bug hid alongside it: for icon-only content, `line-height` doesn't apply (no text line box), so _height_ was also silently content-driven off the icon's own box size (24px/20px) rather than the line-height the two 2026-08-17 fixes were tuned against — it only happened to net out correctly in roomy, where icon size (24px) coincidentally equals line-height (24px); condensed diverges (20px icon vs 16px line-height) and rendered 36px tall instead of 32px. Fixed by adding an explicit `iconOnly` variant to `buttonRootVariants` that forces both `width` and `height` to `--component-button-min-height` and zeroes all padding, so squareness no longer depends on icon-size/padding/line-height tokens agreeing by coincidence. `Button` (the flat wrapper) derives `iconOnly` from `showLabel` internally with no separate settable prop (avoids exposing two redundant "hide the visual label" knobs on its public surface); `Button.Root` still exposes `iconOnly` directly, since the compound API has no `showLabel`/label concept to derive it from. `CloseButton` inherits the fix automatically (see its own dated note above, which needs its recorded dimensions corrected).

**Link, LinkHelp, LinkNavigation — built 2026-08-17, immediately after Button.** Not in the original scope list; the Figma "Links" canvas (165:5251) turned out to contain three genuinely separate component sets — `Link` (169:5374), `Link - Help` (167:5273), and `Link - Navigation` (169:5456) — not one component with variants, so all three were evaluated and built together.

- **`Link-Navigation` is a real configured wrapper around `Link`; `LinkHelp` is not.** Figma itself nests a literal `Link` instance (`Underline=False`) inside `Link - Navigation` next to a chevron — a 1:1 match for "wrapper." `Link - Help` is structurally unrelated: a different type scale entirely (14px vs. Link's 16px, confirmed by `packages/tokens` already having a distinct `component.link.fontSize.help`/`fontWeight.help` bucket pre-dating this build), no `Underline`/`Visited`/`New Window` axes at all. Forcing it onto `Link`'s shape would've been a bad-fit abstraction, not a convenience — it's its own primitive that happens to reuse the same icon-alignment technique internally.
- **`Visited=True/False` is a real `:visited` CSS pseudo-class, never a JS prop** — same "Figma pseudo-class states are never a prop" precedent as `State=Idle/Hover` everywhere else in this file. Text color stays constant even on hover when visited (only the background highlight changes, confirmed against the live frame data — Figma's `Hover, Visited=True` component reuses the same text-fill template as `Idle, Visited=True`). Implemented as `not-visited:hover:text-[...]` / `visited:text-[...]` — Tailwind v4's generic `not-*` variant compiles to a real `:not(:visited):hover` selector, confirmed by compiling it directly rather than assumed.

Screen-reader text (`" (opens in a new window)"`, `sr-only`) is added alongside the icon for the same reason Button's icon-only pattern adds one — the icon alone conveys nothing to a screen reader.
- **`iconVerticalAlign` (`Link`) is a CSS `vertical-align` mechanism, not flexbox** — the "icon immediately follows the last character of wrapped text, bottom-aligned" requirement is fundamentally an inline-flow problem (an icon merged into a text run's own line-wrapping), which `flex-wrap` cannot do (flex items wrap as whole units, not merged into a sibling's internal line breaks). `align-text-top`/`align-middle`/`align-text-bottom` map directly to `vertical-align: text-top`/`middle`/`text-bottom`, confirmed by compiling each. - **`LinkHelp`'s icon alignment went through three iterations before landing — worth reading in full since each one looked right until actually tested.** (1) `align-text-top`, matching the initial "top-aligned on multiline" ask — wrong for the single-line case the user later clarified (text should center against the icon, not sit at its top). (2) Switched to `align-middle` — still inline `vertical-align`, and it overflowed the box: `vertical-align: middle`'s alignment point is the text baseline + half the x-height, which sits _below_ a line box's true center (font ascent typically exceeds descent), so centering a 24px icon there pushes more of it below the baseline than the available leading below can contain, regardless of how tall `line-height` is set — this cannot be fixed by adjusting `line-height` alone, only by abandoning inline `vertical-align` for this case. (3) **Final: flex row (`inline-flex items-start`) with `line-height` pinned to the icon's own size token (`component-link-icon-size-large`, 24px), not a relative multiplier.** A single line of text is then exactly as tall as the icon, so `items-start` (top-aligned to the container) and "centered against line 1" become mathematically the same thing — true for both single-line and wrapped labels, since later wrapped lines just extend the container downward without pulling the icon away from the top. `min-height` was never viable here at any point — `<a>` is `display: inline` by default and ignores `min-height` entirely; `line-height` is the property that actually governs an inline element's box height.
- **`LinkNavigation` renders the chevron as a child of `Link`, not a sibling next to it, departing from Figma's literal nesting.** Figma places the chevron outside the nested `Link` instance as a sibling — a Figma constraint (no true slot primitive for merging content into a nested instance), not real design intent. A pagination control's whole hit target (chevron + text) needs to be one interactive element, especially once `asChild` swaps it to a `<button>`.
- **`asChild` bug, caught in Storybook, not in tests: the chevron went missing entirely when swapped to a `<button>`.** Radix `Slot` requires exactly one child element; the original implementation bypassed all icon-injection logic whenever `asChild` was true (mirroring `Button`/`Link`'s own "consumer owns all content" asChild pattern), which meant the consumer's own `<button>` never got the chevron injected into it at all. Fixed with `cloneElement` — the consumer's single child element is cloned with the chevron composed into _its_ children (preserving the child's own original content), producing one final element for `Slot` to merge props onto. The original `asChild` test only checked that a `<button role>` existed, not that the icon was present — added a dedicated regression test asserting `button.querySelector('svg')` after this was caught, so the gap in test coverage doesn't recur.
- **Underline thickness/offset are hand-added, permanently — not a gap to close in Figma.** Figma's text-decoration properties (style, offset, thickness) aren't Variable-bindable at all, unlike fill/spacing/sizing — so `component.link.underlineOffset` (`{ref.size.02}`, 4px) and `component.link.underlineThickness` (`{sizing.fixed.hairline}`, 1px) exist purely so the code-side CSS values (`text-underline-offset`/`text-decoration-thickness`) have a named token source instead of bare literals, with no Figma authoring action attached.
- **Icon sizing consolidated into one two-step scale, not three duplicate-valued tokens.** `Link`'s own trailing icon is 16px; `LinkHelp`'s leading icon and `LinkNavigation`'s chevron are both 24px (Figma authors this identically in both places, `layout_a111c4b6`, confirmed via re-fetch) — rather than `.help`/`.navigation` tokens with the same value that could silently drift apart, added `component.link.icon.size.default` (16px) / `.large` (24px), shared by all three Link-family components. Caught and fixed before merge, not after — the user asked directly whether the duplicate-valued tokens were worth consolidating.

**API shape, decided directly with the user, several iterations narrower than the first draft:**

- **Compound `Tag.Root`/`Tag.Label` plus a flat `Tag` wrapper for the text-only case** — mirrors Button's pattern. No `Tag.Icon`: content before/after the label (an icon, a dot, a count) is composed directly against `Tag.Root`'s own children (`<Tag.Root><Icon /><Tag.Label>...</Tag.Label></Tag.Root>`), not through a dedicated slot sub-component or `before`/`after` convenience props — both were proposed and cut as redundant once plain-children composition was confirmed to cover the same ground.
- **`variant` (`generic`/`teal`/`red`/`gold`), not `theme`** — `theme` was the first draft's name but collides with `data-theme` (light/dark) and `theme.css`; renamed for the same reason Button's hierarchy axis is called `variant`.
- **No dedicated `backgroundColor`/`textColor`/`borderColor` override props, no CSS-var indirection.** The first draft used a `style`-prop-sets-a-custom-property bridge (the same mechanism `RadioGroup.Group`/`ChecklistGroup.Group` already use internally for `--group-field-*`) exposed as public API. Cut once it became clear color overrides don't need it at all: `cn()`'s `twMerge` already resolves a consumer's own `className` (e.g. `bg-[#ff00aa]`, written as a literal string in the consumer's own source, which Tailwind's build-time scanner sees fine) against Tag's default utility for the same CSS property — no runtime indirection required for a straight 1:1 property override.
- **`borderWidth?: 'default' | 'heavy'`, not an arbitrary CSS-value prop.** Border-width is not a 1:1 property swap like color — the real border stays fixed and a calc'd inset box-shadow supplies the visual difference (same trick as Button's focus ring/Tabs' active border), so box height never moves. Because the shadow's color must match whichever `variant` is active, this is fully static: a `variant`×`borderWidth` `compoundVariants` matrix with every class written as a literal string, not built from a template/variable — the same "Tailwind can't discover a dynamically-assembled class" constraint that motivated the color decision above also rules out interpolating these at runtime. Went through two revisions before landing here: first a three-step `sm`/`md`/`lg` scale (with `md` reusing `control.borderWidth.active` and a new `component.tag.borderWidthHeavy` token backing `lg`), then cut to two steps once no real content needed a third; then renamed `sm`/`md` → `default`/`heavy` — a plain emphasis toggle reads better than a size scale that invites exactly the kind of scale-creep the `lg` step was. `heavy` now reads a new `semantic.control.borderWidth.heavy` token directly (kept from the `lg` step, currently a deliberate duplicate of `.active` — see `HAND_ADDED_TOKENS.md`) rather than `.active`, so the prop value and the token it reads share the same name.
- **Not density-aware — `size` (`sm`/`lg`, mapped from Figma's `Size=Small`/`Large`) is Tag's only sizing axis**, decided directly with the user rather than following every other Primitive's `density` prop.
- **`asChild` supported from the first version**, not deferred to a future interactive variant — Tag renders a `<span>` by default (presentational) but may be composed as e.g. a clickable filter pill via `Slot.Root`, same mechanism as `Button.Root`.
- **`minHeight.large`/`minHeight.small` are hand-computed literals with no Figma source** (both size frames are hug-sized) — derived as `2 × padding.block + lineHeight`, the same border-cancels-out-of-the-height-budget math Button/Tabs already establish.

**Chip — built 2026-08-23, immediately after Dialog. Not in the original scope list.** Figma's `Chip` (145:3802, `docs/FIGMA_COMPONENT_AUDIT.md`) is a single-style component with no color/variant/density axis at all — just `Label` (text) and `Show Close` (boolean). Ships as `Chip.Root`/`.Label`/`.CloseButton` compound API plus a flat `Chip` convenience wrapper (`onDismiss?: () => void`, `dismissLabel?: string`), the same flat-wrapper-over-compound shape Tag established.

- **`Chip.CloseButton` is a bare native `<button>`, not a reuse of `CloseButton`.** `CloseButton` wraps a full tertiary `Button` sized for a standalone control (~40–44px min-height), which would overflow Chip's own tiny box (2px block padding, ~24px line-height) — composing it wasn't an option the way Dialog's close button could. `ChipCloseButtonProps` is just `ComponentProps<'button'>`, not an allow-list `Pick` like `CloseButtonProps` — there's no wrapped component underneath whose future prop growth needs fencing off, so the full native surface is already the correct, complete contract. A TSDoc comment on the type calls out `onClick` as the dismiss hook and states the no-Button-wrapping distinction directly, since that's easy to assume incorrectly from the name alone; the flat `Chip` wrapper maps its own `onDismiss` prop onto that `onClick` when composing `Chip.CloseButton` internally.
- **Tokens are entirely hand-added** — Figma authors no Variables for Chip beyond `Label`/`Show Close`. Colors resolved by exact hex-match against existing semantic aliases (`intent.secondary.subtle`/`intent.primary.subtle`/`content.common.textColor.default`, all already used elsewhere), not picked by name-pattern. `fontWeight` uses `{ref.font.weight.medium}` (500) — Chip is the first component in this family to use `Medium` rather than `400`. Full writeup, including the `borderRadius`/`lineHeight`/`gap` corrections traced to two Figma authoring fixes made mid-session, in `packages/tokens/HAND_ADDED_TOKENS.md`'s `component.chip` entry and the standing-rule bullet above.
- **`cursor-pointer` added explicitly to `Chip.CloseButton`**, same reason Tabs/Card/RadioButton/SelectInput/Checkbox all add it — Tailwind's preflight resets buttons to `cursor: default`, so a real button still needs the utility class to show a pointer on hover.

**SegmentedControl — built 2026-08-24, immediately after Chip. Not in the original scope list; added to the Data display row.** Figma's `SegmentedControl` (155:4365) visually resembles Tabs but is built on Radix `Tabs`, not `ToggleGroup` — SegmentedControl switches the _format_ of the same underlying content (e.g. list vs. map view of the same stores), the WAI-ARIA tabs pattern (`tablist`/`tab`/`tabpanel`), where Tabs switches between different or related content. Ships as `SegmentedControl.Root`/`.List`/`.Trigger`/`.Content`, matching `Tabs.tsx`'s own shape exactly — `List` is the pill-shaped track (Figma's `Slot - SegmentedControl`), `Trigger` the individual segment (Figma's `SegmentedControl-Button`), restyled with the track's inset "Carved" shadow and the selected pill's "Settled" drop shadow instead of Tab's underline treatment.

- Same font-weight layout-shift fix as `Tabs.Trigger` (double-rendered label, one copy invisible and permanently bold to reserve width) — Figma's `Selected=True/False` states are a real 400→600 font-weight change.
- **Sizing borrowed from `Button`'s own density-aware tokens**, not a dedicated sizing set — the Figma frame's inner `Button` instance (102:2513, `variant=tertiary`) confirms these values already match exactly, same borrowed-token precedent Tab set for its own min-height.
- **Hover-state colors are hand-added** — Figma's `SegmentedControl-Button` component set (149:4103) only bound Variables for `State=Idle`; `State=Hover` was never bound at all (unlike Tab). Confirmed the hex values directly against the `Selected=True/False, State=Hover` variants and matched them to two already-existing semantic tokens (`HAND_ADDED_TOKENS.md`, `component.segmentedControl`).
- **`Root` needs `items-start`, not the flex default (`stretch`)** — without it, `List` silently stretches to `Root`'s own width even when no full-width behavior was intended. Caught via a real visual regression the user spotted in Storybook, not self-caught. Full-width usage is `className="flex w-full"` on `List` plus `className="grow basis-0"` on each `Trigger` — plain utility overrides, not a dedicated `fullWidth` prop, matching how `Button`'s own full-width usage works.
- Consumes the `shadow-elevation-carved`/`shadow-elevation-settled` utility classes (see the §1.1 note above) rather than composing the shadow inline.

**FilterMenu — built 2026-08-24, immediately after SegmentedControl. Not in the original scope list.** Figma's `FilterMenu` (142:3014, `docs/FIGMA_COMPONENT_AUDIT.md`) is a header row (a toggle `Trigger` + optional `ClearButton` carrying a count badge) that expands a bordered, shadowed panel (a free-form `Drawer` slot + a `Footer` action row) below it. Ships as `FilterMenu.Root`/`.Header`/`.Trigger`/`.ClearButton`/`.Content`/`.Drawer`/`.Footer`, built on Radix `Popover` — the first real consumer of the still-planned Popover primitive (see the Overlays row above), chosen over `Card`'s `Collapsible` pattern specifically for outside-click/Escape dismissal, confirmed with the user.

- **`Content` renders without `Popover.Portal`** — Figma shows the panel as a plain in-flow child, not portaled to `document.body`, so (unlike `Dialog`/`SelectInput.Content`) it keeps inheriting an ambient `data-density` ancestor for free and needs no concrete `'roomy'` default of its own. A deliberate divergence from the portal-driven-default convention established on `Dialog`/`SelectInput`, not an oversight.
- **`Header` wraps `Popover.Anchor`, not `Trigger`** — `Content` aligns to the whole header row (matching Figma's `HeaderWrap`→`Content` offset), not just the trigger button's own bounds.
- **Figma's `Show Slot Start`/`Show Slot End`/`Show Clear Button` are Figma-only authoring affordances, not code props** — ordinary React composability (children before/after `Trigger`/`ClearButton` inside `Header`, or simply not rendering `ClearButton` at all) already covers them, so `Header` takes a plain `children` slot rather than dedicated slot props.
- **`Trigger`'s "Show Filters" label is `children`, not a hardcoded string** — Figma's `FilterMenuTrigger`/nested `Button` nodes expose no text property, same reasoning already applied to `Dialog.Header`/`.Body`/`.Footer` staying generic slots despite Figma naming them as fixed compounds.
- **`ClearButton`'s count badge reuses `Tag` as-is** (`variant="generic" size="sm"`), with its border color overridden to the brand blue (`className="border-primary"`) at the call site — confirmed via Figma re-fetch that this is a one-off instance-level override on that specific `Tag` instance, not a new formal `Tag` variant. Full writeup in `packages/tokens/HAND_ADDED_TOKENS.md`'s `component.filterMenu` entry.
- **`Drawer` has its own padding/gap, matching `Content`'s own values (12px/8px) — the doubled inset is real and intentional**, not Figma authoring redundancy. An earlier pass dropped `Drawer`'s padding as apparently-redundant with `Content`'s; corrected by the user after visually confirming the doubled inset against Figma's own render. `Footer` keeps its own distinct padding/gap too (12px/16px, a genuinely different gap value from `Content`'s 8px).
- **All new `component.filterMenu` tokens alias through already-verified `surface.*` semantic-tier steps** (`surface.base.default`, `surface.borderColor.default`, `surface.med.gap`, `surface.large.gap`, and a previously-unused-but-real `surface.padding.all` step) — no primitives aliased directly, no invented values. One genuine open gap: `footer.gap`'s condensed-mode value (4px vs. a plausible alternate 8px) couldn't be disambiguated from a single Figma fetch and needs a re-fetch in condensed mode to confirm — see `HAND_ADDED_TOKENS.md`.

**SearchInput — built 2026-08-25, immediately after FilterMenu.** Figma's `Search Input` (145:3867, `docs/PLAN.md`'s Microcopy note above already flagged it as "hand-composed, no error state built yet") is a `TextInput`-style field (nesting the same shared `Input` component TextInput/SelectInput use) joined to a `Button-Primary` into one pill, plus a `Menu-OptionsDrawer` (nesting the same `SelectInput-Option` component SelectInput's own dropdown uses) absolute-positioned 20px inset from the root frame's left edge. Ships as `SearchInput.Root`/`.Label`/`.InputGroup`/`.Field`/`.ClearButton`/`.Button`/`.Microcopy`/`.Suggestions`/`.Option`, built on Radix `Popover` (the second real consumer, after `FilterMenu`) — but unlike every other Radix-backed Primitive in this DS, this one is a genuinely hand-built combobox: Radix ships no `Combobox`/`Listbox` primitive, so keyboard navigation (roving real DOM focus between the field and the option list, not a `data-[highlighted]`/`aria-activedescendant` scheme) is entirely hand-rolled in `SearchInput.tsx`'s `moveFocus`.

- **`Suggestions` (the drawer) portals, unlike `FilterMenu.Content`** — Figma's `Menu-OptionsDrawer` is absolute-positioned within its own frame like `FilterMenu`'s panel, which would normally argue for skipping the Portal (see `FilterMenu`'s own note above). Kept the Portal anyway, a deliberate divergence from that precedent: a search field is likely to end up nested in cards/headers/sidebars across the eventual `apps/locator` app, and the clipping/z-index safety a Portal buys is worth more here than the CSS-cascade convenience of skipping it. Confirmed with the user rather than defaulting silently either way.
- **The drawer's width clamps between two bounds, both derived from the same `CONTENT_ALIGN_OFFSET` (20px) inset applied symmetrically**: the field's own live-measured width (Radix Popper's `--radix-popover-trigger-width`, already tracked via `Popover.Anchor`) as the floor, and Root's own live-measured width (a `ResizeObserver` in `Root`, since `Suggestions` is portaled outside Root's DOM subtree and can't reach a cascaded CSS custom property or a percentage-of-Root `max-width`) as the ceiling — see `SearchInput.tsx`'s own comments for why a `ResizeObserver` was needed here instead of a pure-CSS trick. Landed on the correct math in three passes, not one: an initial version subtracted the 20px offset only from the max bound, overflowing the drawer past Root's own right edge by exactly that 20px; a second pass subtracted it from both bounds equally, overshooting the _default_ (unclamped) case past the field's own right edge instead; the final version subtracts it once from the min bound (so the default width lands flush with the field's right edge) and twice from the max bound (so the grown case stays inset 20px inside Root's right edge too, mirroring the left inset) — each wrong version was caught by the user visually, not self-caught.
- **`SearchInput.Option` deliberately has no persisted "selected" state**, unlike `SelectInput.Option` — picking a suggestion closes the drawer immediately rather than staying checked, confirmed with the user, so `component.searchInput.option` only defines default/highlighted colors, no selected pair. Real `:hover`/`:focus` CSS drives the highlight, not a Radix-managed state, since there's no Combobox primitive supplying one.
- **`component.searchInput`'s drawer/option tokens are their own bucket, not a reach into `component.selectInput`'s**, even though the underlying Figma sub-components (`Menu-OptionsDrawer`'s slot, `SelectInput-Option`) are literally shared with `SelectInput` and resolve to identical values today — matches this file's established per-Figma-component-bucket convention (see `component.textArea`/`component.radioGroup` in `HAND_ADDED_TOKENS.md`) specifically so the two can diverge independently if either component's own Figma authoring changes later. Full writeup in `HAND_ADDED_TOKENS.md`'s `component.searchInput` entry.
- **A new exported DS utility, `highlightMatch`** (`packages/ds/src/utils/highlight-match.tsx`) — bolds the first (default) or, opt-in, every case-insensitive occurrence of a query substring in an option's text. Defaults to first-occurrence-only: bolding every "a" in "Banana" for a one-letter query reads as noise, not an answer to "why did this match," matching the convention most substring-match autocompletes use (GitHub/npm/MDN search) over a fuzzy/non-contiguous matcher's reasons to highlight every character. Always wraps its result in a single outer `<span>`, not a bare Fragment — a real bug found via the user's own visual review: returning multiple sibling nodes let `SearchInput.Option`'s `flex ... gap-[...]` row treat each fragment as its own flex item, inserting the row's gap _between_ the highlighted segments as stray whitespace.
- **`theme.css`'s explicit `@source` globs didn't cover `packages/ds/src/utils/`** — found because `highlightMatch`'s bold `font-[number:...]` class silently compiled to nothing (computed weight stayed 400 for both bold and non-bold text) until `./utils/**/*.{ts,tsx}` was added alongside the existing `./components/**/*.{ts,tsx}`/`./internal/**/*.{ts,tsx}` entries. The same class of gap the original `@source` comment (§1.1) already documented for cross-workspace-boundary scanning, just one directory the first pass didn't anticipate needing.
- **Other real bugs found and fixed during the session, all user-flagged rather than self-caught**: the field's own flex wrapper was missing `min-w-0` (a classic flex-shrink trap — the inner `<input>`'s own `min-w-0` wasn't enough, since the wrapper is itself a nested flex container sharing the row with `Button`), causing it to refuse to shrink below its content's min-content width regardless of Root's actual size; `ClearButton` didn't return focus to the field after clearing, relying on an indirect/async side effect (`Suggestions`' `onCloseAutoFocus`, which only fired in stories that also happened to close the drawer) that left a visible focus-flicker gap — fixed by having `ClearButton` call `fieldRef.current?.focus()` synchronously in its own click handler, the same pattern `Option` already used; and the `Playground`/`DensityComparison` stories' shared `TypeAheadDemo` hardcoded a literal `id="typeahead-search"` for both the field and its label, producing duplicate DOM ids once `DensityComparison` rendered two instances — fixed with `useId()`, the same pattern `SearchInput.tsx` itself already uses internally for `Suggestions`' `contentId`.

## Phase 2: Store Locator (`apps/locator`)

Begins only after Phase 1 exit criteria are met.

### 2.1 Map Implementation

- **Library**: MapLibre GL JS — open-source MIT fork of Mapbox GL JS, no account, no API key. Bundle ~200KB gzipped; acceptable for the showcase.
- **Tiles**: free OpenStreetMap raster tiles (`https://tile.openstreetmap.org/{z}/{x}/{y}.png`). No key required. Looks slightly dated vs vector tiles but is zero-friction and StackBlitz-bulletproof.
- **Upgrade path** (note in code, don't implement): swap tile URL to MapTiler vector tiles for smooth zoom — requires a free account and public API key.
- **Wrapper**: a thin `<Map>` component in `apps/locator/src/components/Map/` that exposes imperative methods (`flyTo`, `setSelected`) via `useImperativeHandle`. Keeps MapLibre out of the rest of the app.
- **Data**: ~6–10 locations in `apps/locator/src/data/locations.ts` — typed array of `{ id, name, category, address, lat, lng, hours, open }`.

### 2.2 Locator UX Features

All four chosen:

1. **Side-by-side map + list** — composed from DS `Stack`, `Card`, `ScrollArea`.
2. **Pin popovers** — clicking a map pin opens a Radix `Popover` (DS export) anchored to the pin, showing store details composed from `Card.Header`, `Badge` (open/closed), `Stack`, and a primary `Button` for "Get directions".
3. **List ↔ map sync** —
   - Click a list row → `mapRef.current.flyTo({ center: [lng, lat], zoom: 14 })`, popover opens.
   - Click a pin → list scrolls to that row (DS `ScrollArea.scrollIntoView`) and row gets a selected style.
   - Single source of truth: a `selectedLocationId` in React state; both views render from it.
4. **Search/filter** — a `FilterBar` product component composed from DS `Input` (name search), `DropdownMenu` (category), `Badge` (open-now toggle). Filtering is client-side over the static array.

### 2.3 Composition Patterns to Showcase

The locator is the proof that the DS composes well. Make sure each of these is visible:

- **Out-of-the-box use**: `Button`, `Input`, `Avatar`, `Tabs` consumed directly.
- **Sub-component composition**: `Card.Root` + `Card.Header` + `Card.Body` assembled into a `LocationCard` product component — not a DS export.
- **Icon composition**: `<Button><MapPin />Directions</Button>` and `<Badge><Clock />Open now</Badge>` — shows the icons package composing cleanly with DS components.
- **`asChild` pattern**: `<Button asChild><a href="...">Directions</a></Button>` for the directions link, proving Radix slot composition works through the DS.
- **Variant extension via cva**: the `LocationCard` extends `Card`'s cva recipe to add a `selected` variant — demonstrates the DS doesn't lock you in.

### 2.4 Phase 2 Exit Criteria

- All four UX features working end-to-end.
- At least three product-level components composed from DS primitives (e.g., `LocationCard`, `FilterBar`, `LocationDetailsPopover`).
- Tokens flow end-to-end from `packages/tokens` through the DS into the locator UI (verifiable by changing a semantic color in the token JSON, re-running the build, and seeing the locator re-skin).
- `pnpm --filter locator dev` boots cleanly on a fresh StackBlitz fork.
